# 工程说明与代码阅读路线

## 一轮请求如何完成

1. `src/App.tsx` 把当前页面的 user/assistant 历史发给 `POST /api/chat`；最后一条是本轮请求。刷新清空历史，不清空任务。
2. `server/app.ts` 使用 Zod 验证消息，并通过 `server/chat-cache.ts` 合并同一幂等键的并发或重发请求。
3. `server/agent.ts` 的 `createAgent()` 接收与任务 API 共用的 `TaskStore`，返回签名仍为 `(messages: ChatMessage[]) => Promise<string>` 的 `reply` 函数。依赖注入让测试能够替换模型，生产入口始终使用 DeepSeek。
4. `server/planner.ts` 把完整历史、真实任务快照和本轮服务端日期交给模型，通过 JSON Output 只规划本轮一个动作，包括 create、list、update_attributes、set_due_date、complete、delete、clarify、help、reminder。
5. 执行器使用严格的 Zod 联合类型验证计划。修改日期、完成和删除前检查 ID 是否存在、多候选和同名歧义，并重新读取存储，拒绝过时计划。
6. 最多执行一次写入；回复使用真实 `create/update/remove` 返回结果生成。查询直接格式化最新存储数据，不让模型自由生成任务列表。
7. `src/TaskPanel.tsx` 在首次加载、聊天请求结束和用户点击刷新后通过 `GET /api/tasks` 重新取数，不用乐观更新伪装执行成功。

## 为什么使用单次结构化计划

本题操作种类少，操作前便能拿到完整任务列表。一次结构化规划比多轮工具调用更容易限制写入次数和诊断错误，也更适合在面试中解释。DeepSeek [JSON Output 文档](https://api-docs.deepseek.com/guides/json_mode/)说明了 `json_object` 和空内容等边界；因此执行器仍必须做类型与业务校验。

模型只做意图与语义匹配：例如把“衣服洗好了”映射到真实的“洗衣服”ID。程序只做确定性的校验和执行。自动化中的模型 mock 不能证明这种语义映射在真实模型上必然正确，必须另做真实联调。

没有新增依赖。`shared/tasks.ts` 提取了原有 API 的标题和更新校验，也用于智能体参数校验，避免聊天和 REST 接口接受不同的标题范围。JSON 存储的同步读写、临时文件替换和未知扩展字段保留行为保持不变。

## 模型与运行模式

默认使用 `deepseek-flash`，可通过 `DEEPSEEK_MODEL` 覆盖型号。每次规划请求显式传入 `reasoning_effort: "none"` 关闭思考模式，适配本题的短 JSON 任务计划。DeepSeek [API 参数说明](https://api-docs.deepseek.com/api/create-chat-completion/)规定省略相关参数时默认开启思考，`temperature: 0` 不能替代这个开关。

该选择是先降低不必要的推理开销，真实语义准确率与延迟仍需联调验证。`server/model.test.ts` 在独立进程中加载配置，经过真实 SDK 并拦截 HTTP 传输，检查默认 Flash、自定义模型、非思考参数和 JSON Output 的实际请求体；测试不使用真实密钥或网络。

## 匹配与澄清规则

- 零候选：明确删除/完成的目标在快照中不存在时，规划器输出对应 action 和 `taskIds: []`，不改成泛化澄清、不挑选无关任务。执行器固定回复“没有找到对应的任务，本轮没有修改任务。请告诉我清单中的任务名称或 #编号。”，不写文件。对象或操作本身不明确时仍澄清。判定器不放宽，回复分类、任务状态、原ID与API/磁盘分别核对。
- 唯一候选：使用存储中真实 ID；完成已完成的任务只说明当前状态，不重复写文件。
- 多候选：按创建顺序列出候选，要求回答“第几条”或 `#短ID`。不会批量猜测执行。
- 同名任务：即使模型只给一个 ID，执行器仍要求当前消息提供明确编号。普通最近指代可由模型结合历史理解；同名时采取更保守的规则。
- 编号：`shared/task-view.ts` 为聊天、规划快照和面板生成相同的全局编号：主任务按创建顺序，每条主任务后紧跟其子任务。筛选、排序保留编号；优先级在主任务之间、同父子任务之间排序，父子保持相邻。操作前核对最近展示清单中的编号与真实 ID，避免增删任务后误操作新的同号任务。短 ID 碰撞时自动增加显示长度，旧的歧义前缀不能消除同名歧义。
- 多编号：不能机械只取句子里的第一个编号；模型判断肯否定和修正意图，执行器核对被选ID与所提编号的唯一映射。同号列表行映射不唯一时拒绝操作，相关伪列表标题场景有回归测试。
- 隐含语义：“算了/先放一放”先确认是否删除；尝试失败或只完成中间步骤不算目标完成；未完成却说“划掉”先区分删除和完成。明确删除未完成任务仍允许执行。
- 同轮要求多个动作：规划器请求拆成单项操作；计划类型本身也不支持多步或任意工具数组。

不同标题之间的语义歧义仍依赖模型是否返回全部候选，不能保证完全消除误匹配。后续可为删除加预览确认、使用服务端保存的澄清状态和更全面的真实模型评测。

真实高干扰案例、最初失败结果及修复后的逐轮状态见 [高干扰测试说明](DIALOGUE_TESTS.md)。无效标题长度会返回具体参数澄清，不与模型服务异常混为一谈。

## 错误和终止

模型 HTTP 超时 20 秒，SDK 自动重试设为 0；整个规划最多 25 秒；前端最多等待 35 秒。每轮一个规划阶段，遇到空白或非法 JSON 时最多重新请求一次，最终最多一次写入，没有工具循环。每轮末尾增加格式提醒，防止历史自然语言回复诱导模型输出任务列表。截断、业务 schema 无效、网络和存储错误不自动重试。总超时会通过 AbortSignal 取消在途模型请求，迟到结果不能执行。

缺密钥、密钥验证失败、请求失败、空白/截断/非法 JSON、非法计划、无效标题、未知 ID、存储读写失败均有中文反馈。SDK 完整错误对象不会进入日志。存储异常时不声称操作成功；无法确认是否写入时提示先查看清单。

## 重复请求与并发边界

前端在同一失败消息原样重试时复用 UUID，并用同步 ref 防止连续点击发出两次请求。服务端将相同键和正文映射到同一个 Promise：即使第一次写入成功而响应丢失，也能重放结果。缓存最多 500 项，结果保留 15 分钟；不同正文复用键返回 409，缓存满返回 503。

这是本题规模下的进程内去重，不是 exactly-once 保证。刷新页面、服务重启、缓存过期或使用新键，均可能再次创建同名任务；REST 创建接口也没有去重。若要跨重启保证，应将请求编号与任务写入放在同一持久化事务中，例如 SQLite 唯一约束和事务。

同一进程内，任务存储同步执行，写入操作之间不会在 JS 事件循环中交错。模型请求期间其他接口修改清单时，执行器拒绝快照过时的完成/删除计划。多个进程共享 JSON 文件仍可能互相覆盖，当前不支持。

## 已实现的选做展示

独立任务面板提供未完成/已完成计数、状态标签、完成任务划线、短ID、组合筛选、优先级排序和手动刷新。用户通过聊天修改任务。筛选和排序只影响显示，旧 JSON 无需迁移。

日期支持见下节；不支持定时通知或具体时刻提醒，不会承诺发送通知。

## 优先级与工作量

- `priority` 为 high/medium/low（高/中/低），`effort` 为 small/medium/large（小/中/大）。工作量是用户指定的粗略估计，没有固定工时换算。每次新建时未指定的属性均省略，由服务端默认 medium，不从同名任务、父任务或历史继承；旧记录缺字段时有效默认值均为 medium；只指定一项时另一项按中。
- 共享 schema 区分存储原貌与有效任务：`storedTaskSchema` 允许字段缺失，`taskSchema` 在读取结果中补默认值。查询不写文件；创建或修改别的记录也不会批量给旧任务补字段。已存在的未知扩展字段保留，非法的已知枚举不静默降级。
- 创建支持直接携带属性。`update_attributes` 的 `changes` 是严格对象，仅允许 priority/effort 且至少一项；不允许 title/done/dueDate。两项修改合并成一次 `tasks.update`，存储只写一次临时文件并原子替换。单项修改不会把另一属性重置为默认值，也不会改标题、完成状态或日期。
- REST 返回存储中的平铺数组，不附带展示编号；`sort=priority` 对数组按字段全局稳定排序。聊天与面板再通过 `taskRows` 生成父子分组展示和保留的全局编号，不能把 REST 数组下标当作聊天编号。
- REST POST/PATCH 支持同样的枚举；GET 支持组合 `status`、`dueDate`、`priority`、`effort` 和 `sort=priority`，非法枚举、空修改及未知字段返回400。实际查询由共享 `filterTasks` 对真实字段求交集，不让模型生成查询答案。
- 面板默认保留父子分组，勾选“高优先级优先”后在主任务之间、同一父任务的子任务之间按高、中、低稳定排序，父子保持相邻，相同优先级维持原有展示顺序。清单显示中文属性，状态和属性筛选可以组合。聊天和面板展示保留全局编号及真实ID，执行器校验最近聊天清单中编号到ID的唯一映射；同名任务仍需明确编号，不能因为排序、筛选或模型只给出一个候选就绕过澄清。
- 规划器只将明确的“紧急/最高优先级”映射为高；属性取值或目标不清先澄清。工作量不根据事项标题、优先级或时长推断。该中文语义判断仍依赖真实模型，严格 schema 能阻止非法字段及枚举，不能证明所有自然语言理解都正确。
- `server/attributes.test.ts` 使用模型mock和真实临时 JSON/HTTP，覆盖默认值、旧数据、创建、单项和双项修改、真实写入计数、组合查询、非法枚举、未知字段、同名澄清、编号及字段隔离。`npm run verify:attributes` 独立运行真实模型18轮对话，逐轮核对ID、API、磁盘及查询展示；结果写入 `reports/attributes-live-latest.json`，不污染开发数据。

## 到期日期与服务端时钟

- `shared/dates.ts` 校验真实公历日期，要求四位年份（0001–9999）和两位月日，拒绝日期滚动、时间戳和无效闰日。`shared/tasks.ts` 中 `dueDate` 可省略；创建不接受 null，修改接受 null 并在存储时移除该字段。读旧文件不填充日期，仍保留其他未知扩展字段；发现非法已存日期时拒绝读取和覆盖。
- `server/task-clock.ts` 读取 `TASK_TIME_ZONE`（默认 `Australia/Sydney`），启动时验证时区。生产入口将同一时钟注入聊天和 REST。测试注入 `now` 函数，避免依赖执行机器的日期和时区。
- 每轮开始固定 `{ today, timeZone }`，规划请求与空 JSON 重试都在最新用户消息前附上它。模型对“今天／明天／后天／昨天”只输出 `today/tomorrow/dayAfterTomorrow/yesterday`，执行器调用 `resolveDate` 按日历解析，不让模型计算今天。跨午夜的在途规划沿用本轮起始日期，下一轮更新；日历加天不受夏令时的23／25小时影响。
- `list` 带日期时默认 `pending`，普通清单默认 `all`；明确包含已完成才输出 `status: all`。共用的 `filterTasks` 在日期上精确匹配，无日期、逾期和其他日期任务不会混入。修改／清除复用原有 ID、编号、同名、并发快照校验；每轮至多一次存储写入，重复设置相同日期或重复清除无日期任务不重写。
- `GET /api/tasks` 保持数组响应，支持绝对 `dueDate` 与 `status` 筛选，并通过 `X-Task-Today`、`X-Task-Time-Zone` 返回服务端日期上下文。面板用这两个响应头判断今日到期与逾期；每分钟、窗口回到前台、聊天结束和手动刷新时重取，持续打开页面的日期可能最多延迟一分钟更新。
- “明天之前”只记录明天这个日期，不承诺某个时刻；缺少年份、日期不清或目标不明先澄清。`reminder` 动作只返回固定能力说明且不写入；用户同意只记录日期后再创建。普通“提醒我买牛奶”仍可作为无时间要求的待办创建。
- 自动化 `dates.test.ts`、`due-date.test.ts`、REST、存储和规划器测试覆盖真实日历、跨日跨年、夏令时、旧数据、日期修改／清除、状态筛选、歧义、非法计划、去重和超时。模型输出使用 mock，不能据此宣称真实模型验证通过。

## 一级子任务与写入边界

- `parentId` 为可选稳定 ID，没有该字段的旧记录视为主任务。`task-rules.ts` 在读取和每次关联修改时验证父任务存在、ID 唯一、自引用、循环和深度；不允许子任务作为父任务，也不允许已有子任务的主任务降级为子任务。JSON 读写保留未知扩展字段，不靠标题关联。
- `TaskStore.create` 的第三个选项对象兼容 priority/effort，并可传 parentId；父任务已完成时，新建子任务与恢复父任务状态在同一个数组上修改，仅调用一次原子保存。`update` 同样处理恢复未完成子任务或重新关联未完成子任务时的父任务状态；写入失败不会部分保存。
- `update(done:true)` 在存储层检查未完成子任务，抛出 `pending_children` 并附未完成列表，REST 返回409，聊天按真实列表回复。所有子任务完成后不自动修改父任务。子任务的日期和属性独立，不继承主任务设置。
- `remove` 默认遇到任何子任务都抛出 `has_children`（包括已完成项），没有写入。显式 cascade=true 才在一次保存中删除主任务及全部一级子任务，保留其他任务。REST 仅接受字面 true/false。聊天还检查本轮明确的一并删除意图或紧邻删除确认的明确答复，不能只靠模型的 cascade:true 授权。
- 规划器用 parentIds 候选数组表示创建/查询的父任务，也可限定完成/删除的所属主任务；执行器验证所有候选存在并为主任务。同名父任务即使模型只选一个也必须澄清；限定父任务后同名子任务仍需编号。所有写操作（包括子任务创建）拒绝规划期间变化的快照。
- 面板与聊天共用 `taskRows` 的 position、parent、完成进度，状态/日期/属性筛选后仍显示子任务所属父任务，避免只见子任务而失去上下文。聊天的缩进列表也参与旧编号与 ID 唯一映射校验。
- `server/subtasks.test.ts` 覆盖六步验收的模型边界 mock、HTTP和磁盘一致性、同名父任务、非法关联、完成规则、确认/级联删除、真实文件写入和替换次数、失败无部分保存、编号及短 ID 碰撞、旧数据、重命名、重新关联、去重和取消。真实模型的语义能力需另行联调；JSON 多进程并发及多层子任务仍不支持。

## 面试可按这五个问题解释

1. 模型如何知道“衣服洗好了”对应哪条任务？读 `planner.ts` 的输入快照、历史和提示词，再解释实际语义能力仍需要真实模型评测。
2. 为什么模型说完成不代表完成？读 `agent.ts` 中 schema、候选校验和 `tasks.update` 的返回值。
3. 为什么刷新不会丢任务？对话在 React 内存，任务由 `task-store.ts` 保存到本地文件，启动时再次从文件读取。
4. 为什么重试不会轻易创建两条？读 `App.tsx` 的 retry ref 和 `chat-cache.ts` 的共享 Promise，同时说明跨重启限制。
5. 测试证明了什么？mock 覆盖可控执行路径，HTTP 集成测试核对真实磁盘，进程测试验证生产装配；浏览器验证 UI，真实模型测试独立验证语义。
